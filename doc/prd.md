# 조직보드 사진 제작 자동화 웹페이지 PRD

상태: 완료

- 문서 버전: v1.0 확정
- 작성일: 2026-09-14
- 확정일: 2026-09-15
- 작성 목적: 조직변경일에 반복되는 조직보드용 사진 제작 업무를 자동화할 제품의 목표, 사용자 흐름, MVP 범위, 출력 규격과 성공 기준을 정의하고 이후 FRD·디자인·TRD·개발 계획의 기준으로 사용한다.
- 참고 자료: [조직도 사진 생성 템플릿](https://docs.google.com/presentation/d/1-WLZOm1n0zlvrfDGhMcjMA3oExH0quy691rvUfES7XA/edit)

## 1. 서비스 한 줄 소개

신규 입사자의 사진과 이름·직군·계약형태를 입력하면 사진을 조직보드 규격에 맞게 자동 편집하고, 이름과 컬러칩을 적용한 사진세트를 A4 인쇄용 PDF로 만들어 주는 웹페이지이다.

## 2. 타깃과 문제 및 현재 대체재

### 2.1 핵심 사용자

1차 사용자는 조직변경일마다 신규 입사자의 조직보드용 사진을 직접 편집하고 출력하는 사내 담당자이다.

초기 버전은 로그인이나 여러 사용자 권한 없이 담당자 한 명이 PC에서 사용하는 로컬 중심 웹페이지로 만든다.

### 2.2 사용자가 해결하려는 문제

현재 담당자는 신규 입사자마다 다음 작업을 반복한다.

1. 서로 다른 크기와 구도의 원본 사진을 조직보드 규격에 맞게 확대·축소하고 위치를 조정한다.
2. 이름을 입력한다.
3. 직군과 계약형태에 맞는 컬러칩을 선택한다.
4. 완성된 사진세트를 인쇄 페이지에 배치한다.
5. PDF로 출력하고 실제 인쇄 크기를 조정한다.

작업 자체는 어렵지 않지만 인원수가 늘어날수록 사진 크롭, 이름 입력, 색상 적용과 페이지 배치를 같은 방식으로 반복해야 한다. 자동 편집이 어려운 사진은 사람의 판단이 필요하므로 완전 자동화보다 “자동 처리 후 필요한 항목만 수정”할 수 있는 흐름이 필요하다.

### 2.3 현재 대체재

1. Google Slides 템플릿에 사진과 이름을 직접 배치한다.
2. 사진 편집 프로그램에서 사진을 한 장씩 자르고 크기를 맞춘다.
3. 직군과 계약형태를 확인해 컬러칩을 수동으로 선택한다.
4. 슬라이드 또는 PDF 인쇄 설정에서 축척을 조정한다.

### 2.4 제품의 핵심 가치

- 여러 직원의 정보와 사진을 한 번에 입력할 수 있다.
- 파일명과 이름이 일치하는 사진을 자동으로 연결한다.
- 얼굴 위치를 기준으로 사진을 먼저 자동 편집한다.
- 자동 결과가 적절하지 않은 사진만 사용자가 직접 보정한다.
- 계약형태와 직군 규칙에 따라 컬러칩을 자동으로 결정한다.
- 사진세트의 크기를 인원수와 관계없이 항상 동일하게 유지한다.
- 별도의 85% 축소 과정 없이 100% 실제 크기로 인쇄할 수 있는 A4 PDF를 만든다.

### 2.5 확정된 범위와 남은 결정

확정된 내용은 다음과 같다.

- 입력정보는 사진, 이름, 직군, 계약형태로 제한한다.
- 소속부서, 소속팀, 직책과 기타 인사정보는 입력하거나 표시하지 않는다.
- 직원정보는 직접 입력하거나 XLSX 파일로 한꺼번에 불러올 수 있다.
- 사진은 여러 장을 한꺼번에 업로드할 수 있다.
- 사진 파일명과 직원 이름을 비교해 자동 매칭한다.
- 동명이인, 중복 사진과 불명확한 파일명은 자동 확정하지 않는다.
- 얼굴인식을 통한 신원 식별은 하지 않는다. 얼굴의 위치와 크기만 탐지한다.
- 자동 편집 후 확대·축소·상하좌우 이동과 초기화를 지원한다.
- 사진세트의 실제 출력 크기는 가로 25mm, 세로 38mm이다.
- A4 가로 용지에 7열 × 3행으로 배치하며 페이지당 최대 21명이다.
- 결과물은 인쇄용 PDF이다.
- 이름 글꼴은 Nanum Gothic을 사용한다.
- 직군·계약형태별 색상은 참고 슬라이드 2의 값을 사용한다.
- 페이지 배치 비율과 간격은 참고 슬라이드 4를 기준으로 한다.
- 외부에 배포하지 않고 사용자의 PC에서 `localhost`로 실행하는 웹앱으로 시작한다.
- 사진 편집, 얼굴 위치 검출과 PDF 생성을 브라우저 안에서 처리한다.
- 직원정보는 XLSX로 관리하고 작업할 때마다 불러오므로 MVP에는 별도 데이터베이스를 두지 않는다.
- 작업 저장과 이전 작업 불러오기는 MVP에 포함하지 않는다.
- 직원 사진과 정보는 외부 AI나 외부 서버로 전송하거나 영구 저장하지 않는다.

FRD 또는 디자인 단계에서 최종 확인할 세부 항목은 다음과 같다.

- 매우 긴 이름이 두 줄에도 들어가지 않을 때의 최소 글자 크기와 경고 방식
- 얼굴 자동 배치에 사용할 기본 얼굴 크기와 눈높이 수치
- 여러 얼굴이 감지되거나 얼굴이 감지되지 않은 사진의 정확한 안내 문구
- 직군 목록에 임원·기타 항목을 추가할 경우 사용할 컬러값

이 항목들은 MVP의 전체 범위를 바꾸지 않으며, 안전한 기본값을 두고 개발할 수 있다.

## 3. 핵심 기능과 부가 기능

### 3.1 핵심 기능 1 — 직원정보 입력 및 XLSX 불러오기

사용자는 직원별로 다음 정보를 직접 입력할 수 있다.

- 이름
- 직군
- 계약형태

여러 명을 한꺼번에 등록할 때는 XLSX 파일을 사용한다.

기본 XLSX 열은 다음과 같다.

| 열 | 필수 | 설명 |
|---|---|---|
| 이름 | 필수 | 조직보드 사진세트에 표시할 이름 |
| 직군 | 필수 | 컬러칩 기본색을 결정하는 값 |
| 계약형태 | 필수 | 직군보다 우선할 컬러칩이 있는지 결정하는 값 |

입력 원칙은 다음과 같다.

- 빈 행은 무시한다.
- 필수값이 빠졌거나 허용되지 않은 값이 있으면 해당 행 번호와 이유를 알려준다.
- 정상 행은 유지하고 오류 행을 구분해 사용자가 수정할 수 있게 한다.
- XLSX의 행 순서는 이후 사진세트와 PDF의 기본 배치 순서가 된다.
- 동명이인은 입력할 수 있지만 사진은 자동 확정하지 않고 수동 매칭 대상으로 표시한다.

### 3.2 핵심 기능 2 — 사진 다중 업로드 및 이름 자동 매칭

사용자는 JPG, JPEG 또는 PNG 사진을 여러 장 업로드할 수 있다.

자동 매칭의 기본 원칙은 다음과 같다.

1. 파일 확장자를 제거한 파일명과 직원 이름을 비교한다.
2. 앞뒤 공백과 불필요한 연속 공백을 정리한 뒤 비교한다.
3. 이름이 한 명에게만 정확히 일치하면 자동 매칭한다.
4. 동명이인이 있거나 같은 이름의 사진이 여러 장이면 자동 확정하지 않는다.
5. 이름과 일치하지 않는 사진은 미매칭 사진으로 표시한다.
6. 사용자는 미매칭 사진을 직원에게 직접 연결하거나 연결을 해제할 수 있다.
7. 한 장의 사진은 한 명의 직원에게만 연결한다.

얼굴인식으로 사진 속 인물이 누구인지 추정하는 기능은 포함하지 않는다.

### 3.3 핵심 기능 3 — 얼굴 기준 사진 자동 편집

사진이 직원에게 연결되면 시스템은 사진에서 얼굴 위치를 탐지하고 조직보드 사진 영역에 맞게 자동으로 크롭한다.

자동 편집의 목표는 다음과 같다.

- 정면 상반신 사진과 유사한 구도를 만든다.
- 얼굴이 좌우 중앙에 오도록 배치한다.
- 머리와 어깨가 과도하게 잘리지 않도록 한다.
- 원본 비율을 유지하고 사진을 찌그러뜨리지 않는다.
- 사진 영역에 빈 공간이 생기지 않도록 기본 확대율을 계산한다.

주민등록증 사진의 공식 기준인 정면 상반신 구도를 참고하되, 자동 크롭에 필요한 구체적인 얼굴 비율과 눈높이는 다양한 샘플 사진으로 검증해 정한다.

얼굴이 없거나 여러 얼굴이 탐지되는 등 자동 편집의 신뢰도가 낮으면 자동 완료로 처리하지 않고 사용자 확인이 필요한 사진으로 표시한다.

### 3.4 핵심 기능 4 — 사진 수동 보정

사용자는 직원별 편집 화면에서 다음 항목을 조정할 수 있다.

- 확대
- 축소
- 위·아래 이동
- 왼쪽·오른쪽 이동
- 자동 편집 결과로 초기화
- 원본을 다시 기준으로 편집 시작

수동 보정 결과는 인쇄 미리보기와 PDF에 동일하게 반영되어야 한다. 사용자가 편집하는 동안 원본 사진 비율은 유지한다.

### 3.5 핵심 기능 5 — 컬러칩 자동 적용

컬러칩은 계약형태와 직군을 기준으로 결정한다.

적용 우선순위는 다음과 같다.

1. 계약형태에 전용 컬러칩이 있으면 계약형태 색상을 적용한다.
2. 계약형태에 전용 컬러칩이 없으면 직군 색상을 적용한다.

직군 컬러는 다음과 같다.

| 직군 | 색상값 |
|---|---|
| 디자인 | `#FFAE01` |
| 서비스 | `#FF01A2` |
| 개발(CE) | `#0196FF` |
| 백오피스(BP) | `#47B50B` |
| QA | `#9900FF` |

계약형태 컬러는 다음과 같다.

| 계약형태 | 적용 방식 | 색상값 |
|---|---|---|
| 정규직 | 직군 색상 사용 | 별도 색상 없음 |
| 계약직 | 계약형태 색상 우선 | `#E6B8AF` |
| 아르바이트 | 계약형태 색상 우선 | `#737373` |
| 파견직 | 계약형태 색상 우선 | `#A4C2F4` |
| 인턴 | 계약형태 색상 우선 | `#00FFFF` |

색상은 화면 미리보기와 PDF에서 동일한 HEX 값을 사용한다. 프린터와 용지에 따른 실제 색 차이는 제품의 색상 계산 오류로 보지 않는다.

### 3.6 핵심 기능 6 — 고정 크기 사진세트 생성

직원 한 명의 사진세트는 사진, 컬러칩, 이름과 외곽선으로 구성한다.

최종 출력 규격은 다음과 같다.

| 항목 | 규격 |
|---|---|
| 사진세트 전체 | 가로 25mm × 세로 38mm |
| 좌우 안쪽 여백 | 약 1.3mm |
| 상단 안쪽 여백 | 약 1.0mm |
| 사진·컬러칩 너비 | 약 22.4mm |
| 사진 영역 높이 | 약 26.3mm |
| 컬러칩 높이 | 약 2.9mm |
| 이름 영역 | 하단 약 9mm |
| 외곽선 | 약 0.6pt, 진한 회색 |

이름 표시 원칙은 다음과 같다.

- 글꼴은 Nanum Gothic을 사용한다.
- 기본 굵기는 800, 기본 크기는 약 12pt이다.
- 기본적으로 가운데 정렬한다.
- 긴 이름은 최대 두 줄까지 줄바꿈할 수 있다.
- 긴 이름은 약 10pt까지 줄여 표시할 수 있다.
- 이름을 임의로 잘라내거나 말줄임표로 숨기지 않는다.

세부 치수는 PDF 출력 검증 결과에 따라 0.1~0.5mm 범위에서 보정할 수 있으나 사진세트 전체 크기 25 × 38mm는 변경하지 않는다.

### 3.7 핵심 기능 7 — A4 페이지 자동 배치 및 PDF 출력

인쇄 페이지 규격은 다음과 같다.

| 항목 | 규격 |
|---|---|
| 용지 | A4, 297 × 210mm |
| 방향 | 가로 |
| 한 페이지 배치 | 7열 × 3행 |
| 페이지당 최대 인원 | 21명 |
| 사진세트 가로 간격 | 약 2.2mm |
| 사진세트 세로 간격 | 약 1.0mm |
| 전체 배치 | 페이지 중앙 정렬 |

페이지 생성 원칙은 다음과 같다.

- 직원정보 입력 순서대로 왼쪽에서 오른쪽, 위에서 아래로 배치한다.
- 21명을 초과하면 22번째 직원부터 같은 규격의 다음 페이지에 배치한다.
- 인원수가 늘어나도 사진세트 크기나 간격을 줄이지 않는다.
- 마지막 페이지의 빈 자리는 빈 칸으로 유지하며 불필요한 카드 외곽선은 표시하지 않는다.
- PDF 페이지 자체에 실제 mm 단위 규격을 기록한다.
- PDF는 프린터 설정에서 `실제 크기` 또는 `100%`로 출력한다.
- 기존 슬라이드에서 사용하던 85% 축소 인쇄는 신규 웹페이지에서 사용하지 않는다.

### 3.8 부가 기능

- 전체 직원 수, 매칭 완료 수, 미매칭 수와 확인 필요 수 표시
- 문제가 있는 직원 또는 사진만 모아 보기
- 사진 업로드 전 기본 XLSX 양식 다운로드
- PDF 생성 전 페이지별 미리보기
- 다음 단계로 이동하기 전에 미매칭·오류 항목 안내
- 현재 작업 초기화

## 4. 화면 목록과 이동 흐름

### 4.1 화면 목록

1. **직원정보 입력 화면**
   - 직원 한 명씩 추가·수정·삭제
   - XLSX 불러오기
   - 입력 오류와 중복 이름 표시
   - 직원 목록과 현재 순서 확인

2. **사진 업로드 및 매칭 화면**
   - 사진 다중 업로드
   - 자동 매칭 결과 표시
   - 매칭 완료·미매칭·확인 필요 상태 구분
   - 사진과 직원의 수동 연결·해제

3. **사진 편집 화면**
   - 직원별 자동 편집 결과 확인
   - 확대·축소·상하좌우 이동
   - 초기화
   - 이름과 컬러칩이 적용된 최종 사진세트 미리보기
   - 이전·다음 직원 이동

4. **인쇄 미리보기 및 PDF 화면**
   - A4 가로 페이지 미리보기
   - 페이지 이동
   - 7열 × 3행 배치 확인
   - 오류 또는 미완료 항목 안내
   - 인쇄용 PDF 생성 및 다운로드

### 4.2 전체 사용자 흐름

```text
새 작업 시작
→ 직원정보 직접 입력 또는 XLSX 불러오기
→ 사진 여러 장 업로드
→ 파일명과 이름 자동 매칭
→ 미매칭·동명이인 수동 연결
→ 얼굴 기준 자동 편집
→ 확인이 필요한 사진만 수동 보정
→ 이름과 컬러칩 적용 결과 확인
→ A4 페이지 자동 배치
→ PDF 생성
→ 실제 크기 100%로 인쇄
```

각 단계는 이전 단계로 돌아가 수정할 수 있어야 한다. 이전 단계에서 이름, 직군, 계약형태, 사진 연결이나 편집 결과를 바꾸면 이후 미리보기와 PDF에 즉시 반영한다.

## 5. 데이터와 개인정보 사용 원칙

### 5.1 작업 중 사용하는 데이터

- 직원 이름
- 직군
- 계약형태
- 원본 사진
- 사진 파일명
- 자동 매칭 상태
- 사진별 확대율과 이동 위치
- 자동 편집 및 사용자 확인 상태
- 계산된 컬러칩
- PDF 배치 순서

### 5.2 데이터 처리 원칙

- MVP에서는 회원가입과 로그인을 제공하지 않는다.
- 작업 저장과 이전 작업 불러오기를 제공하지 않는다.
- 직원정보와 사진은 현재 작업을 처리하는 동안에만 사용한다.
- 새로고침이나 작업 초기화 시 복구되지 않을 수 있음을 명확히 안내한다.
- 직원정보와 사진을 외부 AI 서비스로 전송하지 않는다.
- 얼굴 탐지, 사진 편집과 PDF 생성을 사용자 브라우저 안에서 처리한다.
- 별도 서버나 데이터베이스에 직원정보와 사진을 업로드하지 않는다.
- 개발과 자동 테스트에는 실제 직원 사진과 개인정보를 사용하지 않는다.
- 오류 기록에 직원 이름, 원본 사진이나 사진 파일 경로 전체를 남기지 않는다.

### 5.3 실행 및 데이터 보관 방식

MVP는 사용자의 PC에서 실행하는 로컬 웹앱으로 개발한다.

- 외부 웹주소에 배포하지 않고 PC에서 로컬 실행 명령 또는 실행 파일을 시작한 뒤 브라우저의 `localhost` 주소로 접속한다.
- 사용자가 코드를 수정하지 않고도 한 번의 실행으로 앱을 시작하고 종료할 수 있는 방법을 제공한다.
- 초기 사용자는 한 명이므로 회원가입, 로그인, 사용자 권한과 온라인 계정은 두지 않는다.
- 직원정보는 별도 데이터베이스에 저장하지 않고 XLSX 파일로 관리한다.
- 작업할 때마다 XLSX와 사진을 새로 불러와 사진세트와 PDF를 만든다.
- 작업 상태는 현재 브라우저 세션 안에서만 유지하며 영구 저장하지 않는다.
- 앱의 코드, 얼굴 검출 모델, 글꼴과 필요한 정적 자산은 가능하면 프로젝트에 포함해 인터넷 연결 없이도 실행할 수 있게 한다.

### 5.4 권장 기술 스택

다음 구성은 현재의 권장안이다. 실제 사진과 테스트 PDF를 이용한 기술 검증을 거쳐 `doc/trd.md`에서 최종 확정한다.

| 역할 | 권장 기술 | 사용 목적 | 검증할 내용 |
|---|---|---|---|
| 화면 개발 | React + TypeScript + Vite | 직원정보 입력, 사진 매칭, 사진 편집과 인쇄 미리보기 화면 구성 | Windows PC의 지원 브라우저에서 설치·실행·빌드가 안정적인지 확인 |
| 사진 수동 편집 | `react-easy-crop` + Canvas API | 사진 이동·확대·축소 인터랙션을 제공하고 선택한 영역을 실제 이미지 데이터로 생성 | 편집 화면과 PDF 결과의 크롭 영역이 정확히 일치하는지 확인 |
| 얼굴 위치 검출 | MediaPipe Face Detector (`@mediapipe/tasks-vision`) | 사진 속 얼굴의 위치와 기준점을 찾아 자동 크롭의 시작 위치 계산 | 다양한 사진의 탐지율, 여러 얼굴·미탐지 처리와 처리 속도 확인 |
| PDF 생성 | `pdf-lib` + `@pdf-lib/fontkit` | A4 페이지에 사진세트를 mm 단위로 배치하고 Nanum Gothic을 포함한 PDF 생성 | 25 × 38mm 출력 정확도, 한글 폰트 포함, 파일 크기와 인쇄 품질 확인 |

기술 검토에 사용한 공식 자료는 다음과 같다.

- [Vite 시작 안내](https://vite.dev/guide/)
- [react-easy-crop 공식 저장소](https://github.com/ValentinH/react-easy-crop)
- [MediaPipe Face Detector 웹 안내](https://developers.google.com/edge/mediapipe/solutions/vision/face_detector/web_js)
- [pdf-lib 사용자 글꼴 안내](https://github.com/Hopding/pdf-lib/blob/master/README.md#embed-font-and-measure-text)

기술 적용 원칙은 다음과 같다.

- `react-easy-crop`은 사용자의 이동·확대·축소 값과 크롭 영역을 계산하는 데 사용하고, 최종 크롭 이미지는 Canvas API로 생성한다.
- MediaPipe Face Detector는 얼굴을 누구인지 식별하는 용도가 아니라 얼굴의 경계 상자와 위치를 구하는 용도로만 사용한다.
- MediaPipe 실행 파일과 얼굴 검출 모델을 외부 CDN에서 매번 내려받지 않고 프로젝트에 포함하는 방식을 우선 검토한다.
- 여러 사진을 연속으로 분석할 때 화면이 멈추면 얼굴 검출을 Web Worker로 옮기는 방안을 검토한다.
- `pdf-lib`에 `@pdf-lib/fontkit`을 등록해 Nanum Gothic 사용자 글꼴을 PDF에 포함한다.
- Vite의 TypeScript 변환과 별도로 타입 검사를 실행하는 개발 명령을 둔다.
- XLSX 파일을 읽을 라이브러리는 보안, 라이선스와 브라우저 지원을 비교한 뒤 TRD에서 추가로 선정한다.
- 모든 기술은 외부 업로드 없이 브라우저에서 처리할 수 있어야 하며, 이 조건을 충족하지 못하면 다른 기술로 교체한다.

### 5.5 기술 검증 완료 조건

본격적인 전체 개발 전에 작은 시험 기능으로 다음 항목을 확인한다.

1. 로컬 PC에서 앱을 실행하고 인터넷 연결 없이 기본 화면이 열리는지 확인한다.
2. 구도가 다른 샘플 사진 5~10장을 MediaPipe로 처리해 얼굴 위치가 반환되는지 확인한다.
3. 자동으로 계산한 위치를 `react-easy-crop`의 초기 위치와 확대율에 적용할 수 있는지 확인한다.
4. 사용자가 조정한 크롭 영역을 Canvas 이미지로 만들고 화면 미리보기와 비교한다.
5. Nanum Gothic을 포함한 A4 가로 PDF를 브라우저에서 생성한다.
6. PDF를 실제 크기 100%로 인쇄하고 사진세트가 25 × 38mm인지 자로 측정한다.

이 검증에서 문제가 발견되면 제품 범위를 바로 늘리지 않고, TRD에서 기술 또는 구현 방식을 조정한다.

## 6. 오류 및 예외 처리 원칙

다음 상황을 조용히 무시하거나 성공으로 표시하지 않는다.

- XLSX 파일을 읽을 수 없음
- 필수 열이 없음
- 필수값이 비어 있음
- 직군 또는 계약형태 값이 허용 목록과 다름
- 같은 이름이 여러 명 있음
- 한 직원에게 여러 사진이 연결됨
- 한 사진이 여러 직원에게 연결됨
- 사진 파일 형식을 지원하지 않음
- 사진을 읽을 수 없음
- 얼굴이 감지되지 않음
- 여러 얼굴이 감지됨
- 사진 해상도가 너무 낮아 출력 품질이 부족함
- 이름이 표시 영역에 들어가지 않음
- 미매칭 직원 또는 사진이 남아 있음
- PDF 생성에 실패함

오류는 사용자가 이해할 수 있는 한국어로 표시하고, 문제가 생긴 직원·파일·XLSX 행과 수정 방법을 함께 알려준다. 정상 처리된 다른 항목은 가능한 한 유지한다.

## 7. MVP 제외 범위

첫 번째 버전에는 다음 기능을 포함하지 않는다.

- 인사시스템 연동
- Google Sheets 연동
- 얼굴인식을 통한 이름 식별
- 로그인과 여러 사용자 권한
- 작업 저장 및 이전 작업 불러오기
- 클라우드 데이터베이스
- 여러 조직보드 템플릿 관리
- 배경 제거
- 피부·색감·화질 자동 보정
- PNG 또는 직원별 개별 이미지 다운로드
- 직원정보 외부 공유
- 모바일 앱
- 모바일에서의 정밀 사진 편집 최적화
- 인쇄소 또는 프린터 직접 연결

후속 버전에서 필요성이 확인되면 별도 범위로 검토한다.

## 8. 성공 기준

다음 조건을 모두 충족하면 로컬 MVP가 완성된 것으로 판단한다.

### 8.1 입력과 매칭

- 사용자가 직원정보를 직접 입력하고 수정·삭제할 수 있다.
- `이름`, `직군`, `계약형태` 열이 있는 XLSX를 정상적으로 불러올 수 있다.
- `김현정.jpg`가 동명이인이 아닌 `김현정` 직원에게 자동으로 연결된다.
- 동명이인, 중복 사진과 불명확한 파일명은 자동 확정되지 않는다.
- 사용자가 미매칭 사진을 직접 연결하고 해제할 수 있다.

### 8.2 사진 편집

- 얼굴 한 명이 있는 일반적인 정면 사진은 자동으로 중앙 배치된다.
- 얼굴 미탐지 또는 다중 얼굴 사진은 확인 필요 상태로 표시된다.
- 사용자가 사진을 확대·축소하고 상하좌우로 이동할 수 있다.
- 초기화하면 정해진 기준 상태로 돌아간다.
- 사진이 찌그러지지 않고 원본 비율이 유지된다.

### 8.3 사진세트와 컬러칩

- 모든 직원의 사진세트 크기가 동일하다.
- 계약형태 전용 색상이 직군 색상보다 우선 적용된다.
- 계약형태 전용 색상이 없으면 직군 색상이 적용된다.
- 이름이 Nanum Gothic으로 가운데 정렬되어 표시된다.
- 긴 이름이 임의로 잘리거나 말줄임표로 숨겨지지 않는다.

### 8.4 페이지와 PDF

- PDF가 A4 가로 페이지로 생성된다.
- 페이지당 최대 21명이 7열 × 3행으로 배치된다.
- 22명부터 동일한 사진세트 크기로 다음 페이지가 생성된다.
- 인원수가 늘어나도 사진세트가 축소되지 않는다.
- PDF 내부 사진세트 크기가 정확히 25 × 38mm이다.
- PDF를 `실제 크기/100%`로 인쇄해 측정했을 때 사진세트가 목표 크기에서 ±0.5mm 안에 들어온다.
- 화면에서 확인한 사진 이동, 확대율, 이름과 컬러칩이 PDF 결과와 일치한다.

### 8.5 개인정보와 안정성

- Windows PC에서 로컬 웹앱을 실행하고 브라우저로 `localhost`에 접속할 수 있다.
- 사용자가 코드를 수정하지 않고 안내된 한 번의 실행으로 앱을 시작하고 종료할 수 있다.
- 직원 사진과 정보가 외부 AI 서비스로 전송되지 않는다.
- 직원정보와 사진이 외부 서버 또는 별도 데이터베이스에 저장되지 않는다.
- 인터넷 연결을 끊어도 이미 설치된 앱의 핵심 입력·편집·PDF 생성 기능을 사용할 수 있다.
- 오류가 발생해도 가능한 한 이미 입력하거나 편집한 정상 항목을 유지한다.
- 실제 개인정보 없이 자동 테스트를 실행할 수 있다.

## 9. 검증용 대표 시나리오

개발과 검수에서 최소한 다음 시나리오를 확인한다.

1. 직원 1명을 직접 입력하고 사진 1장을 자동 매칭해 PDF 1장을 만든다.
2. 직원 21명을 XLSX로 불러오고 사진 21장을 매칭해 한 페이지에 출력한다.
3. 직원 22명을 처리해 두 페이지가 생성되는지 확인한다.
4. 동명이인 두 명을 입력하고 같은 이름의 사진을 수동 연결한다.
5. 파일명이 직원 이름과 다른 사진을 수동 연결한다.
6. 얼굴이 없는 사진과 여러 얼굴이 있는 사진의 경고를 확인한다.
7. 가로 사진, 세로 사진, 작은 사진을 각각 편집한다.
8. 계약직 직원에게 직군보다 계약형태 색상이 우선하는지 확인한다.
9. 긴 이름과 공백이 포함된 이름이 잘리지 않는지 확인한다.
10. 출력한 테스트 페이지를 자로 측정해 25 × 38mm 규격을 확인한다.

## 10. 예상 복잡도와 주요 위험

전체 복잡도는 중간 이상이다. 정보 입력과 색상 규칙은 비교적 단순하지만 얼굴 자동 편집과 실제 인쇄 크기 보장은 별도 검증이 필요하다.

주요 위험은 다음과 같다.

1. **얼굴 탐지 편차**  
   원본 사진의 각도, 배경, 해상도와 인원수에 따라 자동 편집 품질이 달라질 수 있다. 자동 결과에 대한 수동 보정 기능을 필수로 둔다.

2. **PDF와 실제 인쇄 크기의 차이**  
   브라우저, PDF 뷰어와 프린터가 자동으로 페이지를 축소할 수 있다. 개발 초기에 눈금자가 포함된 출력 검증 페이지를 만들고 실제 크기 100% 인쇄를 시험한다.

3. **긴 이름의 가독성**  
   제한된 너비에 긴 한국어·일본어·영문 이름이 들어갈 수 있다. 글자 크기 조정, 두 줄 표시와 경고 기준을 FRD·디자인에서 확정한다.

4. **폰트 차이**  
   Nanum Gothic이 사용자 컴퓨터에 없거나 PDF에 포함되지 않으면 줄바꿈과 크기가 달라질 수 있다. 폰트 제공 및 PDF 포함 방식은 TRD에서 결정한다.

5. **대량 사진의 메모리 사용량**  
   고해상도 사진을 여러 장 처리하면 브라우저 메모리 사용량이 증가할 수 있다. 미리보기용 이미지와 최종 출력용 이미지를 구분하는 방식을 TRD에서 정한다.

6. **권장 라이브러리의 실제 적합성**  
   현재 기술 스택은 구현 전 권장안이며 실제 사진, 한글 폰트와 A4 출력 테스트를 아직 완료하지 않았다. 얼굴 검출 속도, 크롭 좌표 일치, 폰트 포함과 출력 치수를 작은 시험 기능으로 먼저 검증한 뒤 TRD에서 확정한다.

## 11. 후속 문서와 개발 전 완료 조건

PRD가 사용자 확인을 받아 v1.0으로 확정되면 다음 순서로 진행한다.

1. `doc/frd.md` — 기능별 입력, 버튼, 상태, 예외와 화면 반응을 정의한다.
2. `doc/design-prompt.md` 및 인터랙션 미리보기 — 네 화면의 구조와 사진 편집 경험을 확정한다.
3. `doc/trd.md` — 권장 기술 스택의 시험 결과를 반영해 브라우저 처리, 얼굴 탐지, 이미지 편집, XLSX와 PDF 구조를 최종 확정한다.
4. `doc/plan.md` — PRD·FRD·디자인·TRD를 EPIC과 STORY로 나누고 각 완료 기준을 적는다.
5. 기본 웹 프로젝트를 생성하고 로컬 실행을 확인한다.
6. `.gitignore`에 `.codex-tmp`, 환경파일과 자동 생성 파일을 제외한다.
7. Git 저장소를 초기화하고 첫 커밋을 만든다.
8. GitHub 비공개 저장소를 연결하고 첫 푸시를 한다.
9. `doc/plan.md`의 첫 미완료 STORY부터 하나씩 개발·테스트·커밋한다.

외부 배포를 하지 않는 로컬 웹앱 방식과 데이터베이스를 사용하지 않는 원칙은 확정한다. 개별 라이브러리와 세부 구현 방식은 시험 결과를 확인하기 전까지 권장안으로 유지한다.
